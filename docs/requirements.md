# MiniMapPrint 要件書

ポケット地図スキル（pocket-map）の GitHub Pages 移植。ブラウザだけで、感熱プリンタ向けの小さい地図（1ビット PNG）を生成する Web アプリ。

- 名称： **MiniMapPrint**（決定 2026-11-15。同名のアプリ・サービスは検索範囲で未発見）
- リポジトリ： tanep3/MiniMapPrint（Tane が作成）
- 公開先： GitHub Pages（静的ホスティング、完全クライアントサイド処理）

## 決定事項（2026-11-15）

### 入力
- ランドマークは最大2つ。地名・住所から Nominatim で解決する（現スキルと同じ）
- 1点のときはその点を中心に、2点のときは両方が収まる範囲にする

### 地図の範囲（縮尺）
- スナップ式スライダー、6段： **500m / 1km / 2km / 3km / 4km / 5km**、等間隔配置、デフォルト 1km
- 2点が選択中の縮尺に収まらない場合は、収まる段まで自動で広げ、**「2点が収まる ○km に広げました」**と画面に表示する（黙って広げない）

### スタイル
- 線画（Overpass のベクタ道路を描画）と、pic2gray4px グレー版（OSM 標準タイルを変換）の**両方を常に生成して並べて表示**する
  - スマホでは縦並び（レスポンシブ）。横並びはしない
- 印刷／保存は、並んだ2枚からユーザーが選んだ方を実行する
- タイトル、ピンとラベル、スケールバー、帰属表示は現スキル（pocket-map）の作りを踏襲する
  - 帰属表示「© OpenStreetMap contributors」は ODbL のライセンス条件として必須

### pic2gray4px
- 変換器は Rust の pic2gray4px を**丸ごと WASM 化**して使う（lib.rs + adjust.rs + autotune.rs + optimizer.rs）。コアは pic2gray4px v0.3.0 に同期済み（2026-11-17）
- **自動調整（contrast / unsharp の auto）も初期版から含める**。WASM 移植では自動調整は変換器と一体で付いてくるため、追加実装として数えない
- グレー版の変換レシピ（2026-11-17 の地図比較で確定）：**イラストモード（拡散なし＋セル間交換）＋赤寄りミキサー＋トーンカーブ normal、unsharp は 0.5 固定、contrast は auto**
  - 根拠：駅前エリアと猿島の 1km 地図（300dpi）で現行コアと比較し、新ロジックの方が道路・緑地・水面の分離が読みやすかった。unsharp の auto は元絵の微差で 0.25／0.5 を往復したため、再現性を優先して固定する（contrast の auto は全サンプルで 1.0 を選んだため据え置き）
- ブラウザ側は Canvas から生ピクセルを WASM に渡す。Rust 側に画像デコーダは持たない

### 出力サイズ
- プリンタ選択の UI 表記は DPI 基準にし、機種は例示にする: **「200dpi（T02等）」「300dpi（M02S等）」**
- 幅はプリンタ別に切り替え：
  - **T02： 384 ドット**（203 dpi × 48mm）
  - **M02S： 576 ドット**（プリントヘッド 576 ドット = 48mm、12 dot/mm。M02S 用ライブラリ群と実機検証記事で一致を確認済み 2026-11-15。48mm × 300dpi の単純計算 567 ではない）
- 高さは現スキルの比率（384×512）を踏襲し、幅に比例させる（T02： 512、M02S： 768）

### 出力・印刷の導線
1. **共有**： 画像タップ → クローズアップビュー → 共有ボタン（Web Share API）で OS の共有シートを出し、Phomemo アプリへ渡す（スマホの本線）
2. **ファイル保存**： PNG をダウンロードする（予備導線。保存 → Phomemo アプリで開いて印刷、も可能）
3. **PC ブラウザ印刷**： 用紙幅に合わせた印刷レイアウト（@page）を用意し、ブラウザ印刷 → 自宅 CUPS サーバ経由で印刷する（Tane の使い方）。他ユーザーの前提は 1 と 2

### プラットフォーム
- **PWA** にする（ホーム画面追加、アプリ風起動）。iPhone Safari でも動作させる
- ただし地図生成はオンライン前提（Nominatim / Overpass / タイル取得が必要）。PWA でオフライン化するのはアプリの外枠のみ
- 画面デザインは Voice2QR と同じ「エモい」方向
- **UI 言語は Voice2QR と同じ方式**： デフォルトは端末の言語に合わせ、日英切替を用意する

### リリース・運用（Voice2QR 方式に揃える）
- 開発・運用は基本的に Voice2QR で培った方式で進める
- リリースは**タグ駆動**： `v*` タグの push で GitHub Pages のワークフローを起動し、タグのコミットからビルドして掲載する
- アプリのバージョンはタグと一致させる（`package.json` の `appVersion` ＝ タグから `v` を除いたもの。タグを打つ前に上げる）
- **バージョン番代: 実機確認用は v0.1.0 番代、正式リリースは v1.0.0 番代**とする
- バージョン埋め込みとキャッシュ対策を最初から入れる： バージョンを Service Worker のキャッシュ名と version.json に刻み、起動時に照合して古ければ一度だけ強制リロードする
- **Cache Storage はオリジン単位で共有される**（スコープ単位ではない）ため、キャッシュ削除は `minimapprint-` 接頭辞のものだけに限定する（Voice2QR v1.0.4 の教訓）

### データ取得と CORS（実測済み 2026-11-15）
- Nominatim、OSM タイル、Overpass API はいずれも `Access-Control-Allow-Origin: *` を返し、ブラウザから直接取得できることを実測で確認済み
- Overpass への POST は Content-Type を `application/x-www-form-urlencoded` にしてプリフライトを回避する
- OSM のタイルポリシーを守る： 要求された範囲だけ取得（現スキル同様、最大16タイル目安）、一括取得・プリフェッチをしない

## スコープ外（初期版ではやらない）
- **Web Bluetooth でプリンタを直接叩く印刷**： Tane が Phomemo を購入した後に実装研究する
- 経路（ルート）表示： 現スキル同様、2点間もピンとラベルのみで経路は描かない

## 追記（2026-11-15、v0.2.0）: 線画のデータソース変更

- 背景: Overpass は小さいクエリでもサーバ側の順番待ちで約30秒かかり（2026-11-15 実測）、実用に耐えなかった。エンドポイントの並行レース（v0.1.4）で待ちの上限は最速サーバに揃えたが、それでも混雑時は遅い
- 決定: 線画の主データソースを **ベクタタイル（Versatiles、Shortbread スキーマ）** に変更する。タイルは CDN 配信の事前生成データで、抽出はブラウザ内で行う（実測: 新宿2km で約2.4秒）。ベクタタイルが失敗した場合のみ Overpass（並行レース）にフォールバックする
- 受け入れたトレードオフ:
  - ジオメトリはズーム14で一般化済みのものを使う。1km 以上の地図では実用上問題ないが、500m の地図では角の丸みが目立つ可能性がある
  - タイルは建物・POI を含む丸ごとファイル（新宿 z14 で 554KB/枚）のため、転送量は Overpass の JSON より増える。CDN 配信なので時間は短い
  - データの鮮度はタイル生成元の更新周期に依存する（Overpass のような即時反映ではない）

## 追記（2026-11-18、v0.4.0）: 近所モード（中心合わせ＋250m/100m）

- 背景: 利用者（Tane の友人）からの要望。自宅住所を入れてもジオコーディングの精度では中心が合わず（日本の番地は Nominatim にほぼ無い）、「任意の場所を指定して印刷したい」「500m より寄りたい（近所の地図を地域の集まりで配る）」。実測で裏取り済み（駅前エリア中心、2026-11-18）:
  - グレーは 250m（z18）・100m（z19）とも道路・路地・建物の輪郭まで読める
  - 線画のデータは z14 一般化ベクトルで、限界は解像度ではなく範囲に入る線の本数。駅前では 250m で streets 12件、100m でも 7件あるが、住宅街の中心では 100m で線が 1〜2 本だけになる場所がありうる（未実測の外挿）。グレーは z19 ラスタがあるため 100m でも成立する
- 決定（2026-11-18、Tane）:
  - **縮尺は8段**： **100m / 250m / 500m / 1km / 2km / 3km / 4km / 5km**、デフォルト 1km は継続。200m は 250m と近すぎるため入れない
  - **原画プレビュー**: ランドマーク検索の導線は残す（加算）。検索で表示された場所を起点に、OSM ラスタの原画を線画カードの上に配置し、そこで**ドラッグ移動／ピンチ／マウスホイール／Ctrl+プラマイで拡大縮小**して、「この範囲で描画」ボタンで中心と範囲を確定してから線画・グレーを生成する
    - 操作中は取得済み画像の変形で追随し（レスポンス優先）、手を離したところで必要なタイルを取り直す。プレビューの取得範囲は表示範囲より一回り大きくし、ドラッグで端が欠けないようにする（取得量は従来どおり最大16タイル目安を維持し、収まらなければズームを下げる）
    - 拡大縮小の確定時は最寄りのスナップ段に寄せ、スライダー表示と同期する
  - **現在地ボタン**: Geolocation API で現在地を取得し、そのままその場所の地図生成まで進む（HTTPS 前提。GitHub Pages は HTTPS のため可）
  - **スライダーのラベル位置修正**: ラベルをつまみ中心の移動軌跡に合わせて配置する（従来は flex のセル中央配置で、つまみ位置と構造的にズレていた）
- 受け入れたトレードオフ:
  - 100m の線画は場所によってほぼ白紙になりうる。仕様として許容し、100m ではグレーが本命という位置づけにする（UI で強制はしない）
  - 手動で中心を動かした場合、ピンが印刷範囲の外に出ることがある。そのピンは描かない（タイトル表記は元のまま）

## 追記（2026-11-19、v0.5.0）: 検索の再設計（住所・海外・同名対策）

- 背景:
  - 住所形式の入力が Nominatim では 0 件か丁目中心点止まり（OSM に日本の番地・号の住所点データがほぼ無い）。友人ユーザーの「自宅住所で中心がズレる」苦情の根本原因はこれ
  - 日本語モードは `countrycodes=jp` 固定だったため、海外の場所が引けない
  - 同名施設は、その施設自体が OSM に登録されていなければ原理的に出ない（実測で確認: ある市立の文化施設が OSM に一切登録されておらず、検索では他地域の同名施設しか返らなかった）。これはデータ不在であり検索ロジックでは直せないため、「見つからない」場合の案内を原画プレビューでの位置合わせに繋ぐ
- データ源の選定（実測と一次情報で確認済み）:
  - **国土地理院 住所検索 API**（`msearch.gsi.go.jp/address-search/AddressSearch`、実体は東京大学 CSIS シンプルジオコーディング）: 無料・キー不要・CORS `*`。住居表示地域では号の点まで一致（実測: 世田谷区三軒茶屋2-14-9 → １４番９号の点）、地番住所も可（鎌倉市山ノ内8）。大きな街区では番止まりの場合がある（西新宿2-8-1 → 二丁目８番の点）
  - **留保**: GSI の公式見解では、検索機能は地理院地図向けであり外部利用への長期提供は保証されず、仕様も無予告で変わりうる（gsimaps Issue #29）。よって GSI は「先に試す第一候補」に留め、失敗・不一致のときは必ず Nominatim に倒れる設計とする。なお GSI の「地名検索」は同一エンドポイントであり、施設検索の別口は存在しない（gsimaps のソースで確認）
  - 施設名を引ける他の候補は無いことを確認済み（CSIS は住所のみ、Photon 等は同じ OSM データ、Wikidata は当該施設 0 件、商用 API は有料キーと利用条件が本アプリの「キーなし・完全クライアントサイド」の形に合わない）
- 検索パイプライン（`searchPlace`、UI 言語が ja の場合。en は従来どおり Nominatim 全世界検索のみ）:
  1. **日本語を含まないクエリ** → Nominatim 全世界検索のみ（GSI・jp 絞りを経由しない）
  2. **住所らしいクエリ** → GSI を先行する。住所らしさの判定は、数字を正規化したうえで「丁目／番地／数字+番／数字-数字／末尾の数字（地番形式）」のいずれかを含むこと
     - **GSI 採用条件**（GSI は住所でない入力にもファジーに何らかの住所を返すため、そのままは採用しない）: 返却された住所（title）を正規化（全角→半角、漢数字→算用数字）し、(a) 地域部分（最初の数字より前）が都道府県を除いて一致するか前後どちらかに含まれる、(b) クエリに市区町村名があれば title にも含まれる、(c) 双方に最初の番地数があれば一致する、を全て満たすものだけを候補とする。1 件なら確定、複数なら候補ピッカー表示、0 件なら次へ
  3. **Nominatim（countrycodes=jp）**。ヒットすれば採用する。ただし全候補の importance 最大値が 0.01 未満の場合に限り全世界検索も行い、その先頭候補の importance が 0.5 以上なら全世界側の結果セットを採用する（同名の小規模 POI への誤爆対策。実測: 「ニューヨーク」→ jp では府中市の pub（importance 0.00009）、全世界では New York 市（0.88））
  4. jp で見つからなければ **Nominatim 全世界で再検索**（海外フォールバック）
- 検証: 実クエリ 8 件のモジュールテストで全件期待どおり（2026-11-19）: 住居表示の号まで一致／大きな街区の番止まり／漢数字表記／地番住所／駅名（Nominatim 経路）／英字クエリの全世界直行／同名施設（既知の限界として記録）／カタカナの海外地名（誤爆ガードで New York の候補提示）
- 既知の限界:
  - OSM に無い施設は検索では出ない（データ不在）。見つからない場合のメッセージから、近くの駅・住所＋原画プレビューでの位置合わせに案内する
  - GSI が番止まりの場合、点の位置が実際の番地から大きくずれることがある（実測で約 100 m、隣接地区に点があった例あり）。v0.5.1 で一致レベルの警告表示を追加。原画プレビューで補正可能
  - importance ガードの条件（0.01 未満／0.5 以上）に当てはまらない同名衝突では、国内側が優先されることがある

## 追記（2026-11-19、v0.5.1）: GSI の一致レベル表示

- 背景: GSI の返す点の精度は地域のデータ整備度で大きく違う。号レベルまで入っている地域がある一方、番レベル止まりの地域では点の位置自体が信用できない実例を確認した（2026-11-19 実測: title は番まで一致したのに、返った点はその番地ではなく隣接する別地区側にあり、実際の場所から約 100 m ずれていた）。つまり title の一致レベルは位置の正確さを保証しない。粗い一致のピンを正確だと信じて現地へ行ってしまう事故を防ぐため、一致レベルと「ピンは目安」という警告を利用者に明示する
- 実装: GSI の採用時に title の最も細かい住所要素から一致レベルを判定する（号 = go／番・地番 = ban／丁目 = chome／町名のみ = area）。番以下の一致では、生成ボタンの下に注意書きを出す（例: 「住所は番地まで判別できましたが、ピンの位置は目安です。実際の場所と 100 m 以上ずれることもあるので、原画プレビューで必ず確認してください。」）。号レベル一致と Nominatim 由来の結果では出さない。原画プレビューで自分で範囲を確定した場合と、入力を書き換えた場合にも消す

## 追記（2026-11-19、v0.5.2）: GSI の点を OSM で照合する警告

- 背景: v0.5.1 の「号レベルなら警告なし」には穴があった。ある地域では、街区の点が号レベルまで含めて丸ごと隣の地区にずれて登録されており（実測: 逆ジオコーディングで隣接地区と判明、実際の場所から約 100 m）、号まで一致しても無警告で誤った場所を指した。title の一致レベルでは点の位置の正しさは判定できない
- 照合ロジック: GSI 由来の点について、OSM（Nominatim 逆ジオコーディング）でその点の地区（町名）を取得し、クエリの町名と比べる。**食い違いが確実な場合だけ**強い警告を出す（「ピンの位置を別の地図データで照合したところ、住所の町名と違う場所を指しています」）。地区データが無い・取得失敗・判定不能の場合は何もしない（無実の点に警告を出さない）。住所らしいクエリでのみ照合する
- 検証（2026-11-19）: ずれた街区の号点・番点 → mismatch（警告）／正常な号点（都内の住居表示地域）・地番住所の点 → ok（無警告）／ランドマーククエリ → 照合対象外

## 追記（2026-11-19、v0.4.1）: 候補リストの残り表示を修正

- 不具合: 曖昧検索で表示した候補リスト（「どちらの場所ですか？」）が、入力欄の文字列を書き換えても消えずに残った（Tane の実機スクリーンショットで確認）。入力と無関係な候補が表示され続けるのは誤操作のもとになる
- 修正: 入力欄を編集したらその欄の候補リストを消す。再検索の開始時にも消す。あわせて、解決済みの場所は「解決したときの文字列」と現在の入力が一致する間だけ有効とし、入力を書き換えたら破棄する（入力を空にしても古い場所で生成される、という同種の残りを防ぐ）

## 追記（2026-11-19、v0.5.3）: 保存ファイル名の上書き対策

- 背景: 保存・共有のファイル名が `minimapprint-line.png`／`minimapprint-gray.png` の固定名で、保存先で前回保存した地図が上書きされて消えた（Voice2QR で先に発見し、同じ仕様でこちらにも適用）。Web アプリからは保存先に同名ファイルがあるか確認する手段がないため、存在チェックではなく名前自体で衝突を避ける
- 仕様: デフォルト名はスタイル名＋秒までのタイムスタンプ（例: `minimapprint-line-20261119-131500.png`）。同一セッションで同名が再生成されたら `-2`、`-3` を付ける。結果カードと拡大モーダルの両方にファイル名欄を置き、ユーザーが自分で付けた名前は意図としてそのまま使う（その場合は上書きもありうる）。モーダルを開くと、そのカードの名前欄の内容と編集状態を引き継ぐ

## 追記（2026-11-19、v0.5.4）: ファイル名欄の撤去

- v0.5.3 で入れたファイル名欄（結果カード＋モーダル）は、同日の判断変更で撤去した。秒までのタイムスタンプと連番で名前の一意性は担保されるため、命名 UI は一般の利用者にとって余分な表面と判断した。保存・共有は従来通り1タップで、名前は生成のみ。将来自命名が必要な場面が出たら、常設の欄ではなく保存時のポップアップで出す形にする
